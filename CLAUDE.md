# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

helm is a homelab dashboard: a Bun server (`server/`, TypeScript) that proxies and normalizes [Glances](https://nicolargo.github.io/glances/) metrics for any number of nodes, controls local containers and compose stacks, sends ntfy alerts, and exposes a real PTY over WebSocket — plus an Ionic Vue 9 frontend (`src/`, plain JS components, iOS mode everywhere) built with Vite, meant to be installed as an iPhone home-screen web app. README.md is detailed and authoritative on behavior and the reasoning behind it.

## Commands

```sh
bun install
cp config.example.json config.json   # optional; without it the server starts in setup mode (code in the log and ./setup-code)
bun dev              # Bun server on :3001 (--hot) + Vite on :5173 together
bun run dev:server   # server only
bun run dev:web      # Vite only (HELM_SERVER overrides the proxy target, default http://127.0.0.1:3001)
bun run build        # vue-tsc && vite build → dist/
bun run lint         # eslint (the Ionic scaffold's config, .eslintrc.cjs)
bun start            # production: serves dist/, /api and /pty on :3001
```

There is no test suite. The only typecheck is the `vue-tsc` step of the build, and with `allowJs` but no `checkJs` it checks only the TypeScript, not the plain-JS components. Verify server changes by running it and hitting endpoints (e.g. `curl localhost:3001/api/health`, `curl -X POST localhost:3001/api/alerts/sweep`). To exercise first-run setup in dev, move `./config.json` aside (and make sure no `~/.config/helm/config.json` or `/etc/helm/config.json` exists, or set `HELM_CONFIG` to a missing path) and restart; setup writes `./config.json` and keeps the code in `./setup-code` (both gitignored).

## Things that are easy to get wrong

- **`dist/` is committed and is the deployment.** Servers run `git pull && systemctl restart helm` straight from the checkout — nothing builds on the box. Any frontend change must be followed by `bun run build` and committing the regenerated `dist/`, or it never ships.
- **The server must have no runtime dependencies.** `server/` imports only Bun built-ins and `node:*` modules so an install is `dist/` + `server/` with no `node_modules`. The npm dependencies in `package.json` are frontend-only (bundled by Vite).
- **Glances requests must stay sequential and minimal** (`server/glances.ts`). Glances computes CPU/IO percentages from deltas against its own last sample, so concurrent plugin requests corrupt each other's readings. Never call `/all`; add new plugins to `PLUGIN_TTL_MS` with the slowest TTL that works. Fetches happen only when a browser asks, cached so multiple viewers coalesce into one fetch (`refreshMs * 0.8` freshness floor). The only timer-driven polling is alerts (`server/alerts.ts`).
- **Pages stay mounted.** Ionic tabs keep every visited page alive after you leave it, so `onMounted`/`onUnmounted` do not mean "on screen". Every poller (`useMetrics`, `useFleet`, `useStacks`) takes `usePageActive()` from its page and pauses while the page is off screen — forget it and every page you ever visited keeps polling Glances. For enter/leave work use `onIonViewWillEnter`/`onIonViewWillLeave` (or `onIonViewDidEnter` once the transition has finished, e.g. to measure).
- **Pages read their query with `useQuery()`, never `route.query`.** `useRoute()` is always the *current* route, so a background page reading it would see (and react to) another page's query. `useQuery` freezes while its page isn't current; `setQuery` merges and replaces without a history entry.
- **The process list is expensive** — fetched only while that panel is open (`wantProcesses` in `useMetrics.js`).
- **`ion-refresher` goes in `HelmPage`'s `fixed` slot.** It must be a direct child of `ion-content`; the default slot is inside the page gutter.
- **`src/theme/variables.css` selectors are `:root, :root.ios, :root.md` on purpose.** Ionic's dark palette is scoped to `:root.ios` (and `:root.ios ion-modal`); plain `:root` loses to it and paints items, cards and sheets pure black. The `--ion-color-*` sets need literal values per scheme, not `var()`.
- **The origin check is the CSRF boundary — never widen it.** Browsers apply no CORS to WebSockets or simple POSTs, so `originAllowed()` (`server/index.ts`) gates every mutating method in `guard()` and both upgrades (`/pty`, `/api/stacks/stream`) via `refuseUpgrade()`. No `*`, no reflecting the request's Origin, no `null`; extra origins only through `server.allowedOrigins` (exact origins, validated in `config.ts`). Don't add `rewriteWsOrigin` (or otherwise rewrite Origin) in the Vite proxy — dev passes via `Sec-Fetch-Site`/the `X-Forwarded-Host` that `forwardHost` stamps, and rewriting Origin would let any page through the dev server.
- **Setup mode is a lockdown — never open more routes during it.** Unconfigured means no config file at any search path and no `HELM_NODES` (`loadConfig().configured`). Until setup finishes, `guard()` and `refuseUpgrade()` answer 409 for everything except `/api/config` (`OPEN_DURING_SETUP` in `server/index.ts`); `/api/health` (open) and `/api/setup/*` (own wrapper in `server/setup.ts`: `cors()`, origin check for mutations, token if `HELM_TOKEN` set one, then `X-Helm-Setup-Code`) are the only other ways in. Above all the terminal stays shut — it could read the setup code off disk. `/api/admin/*` is refused (409) while unconfigured, since with no token it would let anyone write the first config; `/api/setup/*` is refused (409) once configured. New routes go through `guard()` and inherit this.
- **Config writes go through `server/setup.ts` only.** `parseEdits` → `applyEdits` onto the raw file (`readRawConfig`) → `buildConfig` validation → `writeConfigFile` (temp file + fsync + rename, mode 600; in-place fallback when an old install's root-owned `/etc/helm` blocks the temp file) → `reload()`, serialized by `exclusive()`. Edits replace only `nodes`/`services`/`commands` and `stacks.dir`/`command`/`template`/`envTemplate`; every other key, unknown per-node keys and saved Glances passwords are preserved (passwords never leave the server — `hasPassword` only). Never write the merged `Config` back (that would bake env overrides and defaults into the file). Nodes from `HELM_NODES` are not editable (409 if changed).
- **`reload()` (`server/index.ts`) mutates the one `config` object in place**, so handlers must read `config.x` at request time, never capture it at startup. It rebuilds `nodesById`, calls `forgetNode` for nodes removed or reached differently (url/api/credentials), restarts the alert timer, and flips `state.configured`. `server.*` is excluded — host, port and `allowedOrigins` (captured in a `Set`) need a restart. Only setup and Settings saves call it; hand edits to the file still need a restart.
- **`$HELM_CONFIG`, when set, is the only config path** (`CONFIG_PATHS`), even if the file doesn't exist yet, because it is also the write target (`configWriteTarget`). Don't reintroduce fall-through: it would read one file and write another, and a stray `~/.config/helm/config.json` would hide setup.
- **PTY spawning**: pass `terminal: {...}` options inline to `Bun.spawn`, never a prebuilt `new Bun.Terminal(...)` — only the inline path calls `setsid()`, without which job control (Ctrl+C/Z, fg/bg) breaks. See `openPty` in `server/index.ts`.
- **Command execution is argv-only**, never shell strings. Container names are validated against the live list; stack names are validated and resolved inside the stacks dir before any delete. Mutating actions are POST/PUT/DELETE only.
- **Stack defaults live in `server/stacks.ts`** (`DEFAULT_STACK_TEMPLATE`, `DEFAULT_ENV_TEMPLATE`, `defaultComposeCommand`). `null` in the config means "the built-in default", and `setup.ts` stores `null` for any submitted value equal to it, so keep defaults generic (no machine-specific networks or absolute paths) and never reintroduce a client-side fallback template — `/api/config` already sends the effective text. `stacks.dir` is validated in `setup.ts` (absolute, existing, not `/`, `$HOME` or a system root) and `deleteStack` refuses a folder with no compose file; both guard the recursive delete.
- **Container and stack actions are local-node only.** Glances is read-only, so actions shell out to `podman`/`docker` on the server's own machine. `nodeIsLocal` (`server/containers.ts`) detects this by matching the Glances hostname, overridable with `"local": true/false` on a node; `/api/nodes/:id/capabilities` tells the UI which buttons to show.
- **Destructive actions confirm with `useConfirm()`** (the native iOS action sheet), not a custom dialog or a two-tap button.
- **Settings is a modal, not routes.** It's reachable from every tab, and Ionic puts a view shared by all tabs in a modal rather than routing it into whichever tab you're on. Open it with `useSettings().open(section?)`; its sub-pages are an `ion-nav` stack (`ion-nav-link` / `pushPage`), so never add `/settings*` routes. ion-nav pages get no `onIonView*` hooks in Vue (only `ion-router-outlet` fires them): load in `onMounted`, refresh lists with `onConfigSaved` (`settings/editing.js`). A new editor must use `useUnsavedGuard` (and pass `guarded` to `SettingsView`) so `canDismiss`, the guarded Back, the disabled swipe-back and `beforeunload` all cover it.
- **Only the tab bar switches tabs.** Page content never links into another tab (no "All apps" or "Go to Machines" shortcuts); links within a tab are Ionic components with `router-link`, or `useIonRouter`. `ion-router-link` is for vanilla/Stencil apps — not in Ionic Vue.
- **Text sizes are rem, never px.** `typography.css` sizes `<html>` from the iOS system text size (Dynamic Font Scaling), so anything in px ignores the user's setting. The terminal's xterm `fontSize` (a number, not CSS) is scaled from the root font size for the same reason.
- **Never patch `ion-modal` `breakpoints` to `undefined`** — Ionic crashes going from an array to nothing. `BottomSheet` keys its `ion-modal` on wide/narrow so it remounts instead.
- **Alerts**: `containerCrashed` fires only for `restarting`/`dead`, never `exited` (a manual stop). Utilisation rules default to `null` (off) deliberately — don't flip them on in defaults.

## Architecture

**Server (`server/index.ts`)** — one `Bun.serve` with a `routes` table. Every route except `/api/health` and `/api/setup/*` is wrapped in `guard()`: the setup-mode 409 (see above), then `cors()` (answers preflights and adds `Access-Control-Allow-Origin` only for `server.allowedOrigins`), then the origin check for mutating methods, then the optional token (`X-Helm-Token`, `Authorization: Bearer`, or `?token=`). `/api/health` is open (CORS-wrapped, no token) so Settings can tell "unreachable" from "wrong token". Two WebSocket kinds share one `websocket` handler, discriminated by `ws.data.kind`: `'pty'` (keystrokes binary, control frames JSON like `{type:'resize'}`) and `'stack'` (streams a compose job's output); both upgrades go through `refuseUpgrade()`. Unmatched non-`/api` paths fall back to serving `dist/` as an SPA.

- `config.ts` — loads `$HELM_CONFIG` alone if set, else the first existing of `./config.json`, `~/.config/helm/config.json`, `/etc/helm/config.json` (`readRawConfig`); `buildConfig` merges onto `DEFAULTS`, normalizes (including `server.allowedOrigins`, rejecting `*`/`null`/paths at startup), then applies `HELM_*` env overrides (used by the systemd unit). `loadConfig` reports `configured`; `configWriteTarget` is where setup/Settings write (`$HELM_CONFIG`, else the loaded file, else `./config.json`). The `normalize*` helpers are shared with `setup.ts`. Types for every config section live here.
- `setup.ts` — first-run setup and the Settings editor. Setup code (8 chars from an unambiguous alphabet, shown `XXXX-XXXX`, kept in `setup-code` mode 600 beside the config write target so it survives restarts, constant-time compare, deleted when setup completes), the rate limit (10 wrong codes per 10 minutes, global, in memory → 429), EditableConfig parse/merge, the atomic writer, and the routes: `/api/setup/verify`, `/api/setup/local`, `/api/setup/probe`, `POST /api/setup` (optional `token: 'generate'` mints a 32-byte base64url `auth.token`, returned once; refused if `HELM_TOKEN` is set), and `/api/admin/config` (GET/PUT), `/api/admin/local`, `/api/admin/probe` behind `guard()`.
- `glances.ts` — TTL-tiered client plus normalization into a compact snapshot, so the frontend never deals with raw Glances shapes or per-node plugin availability. Also history backfill for sparklines, `forgetNode` (drop a node's cache on reload), and `probeGlances` (setup/Settings Test: a server-side fetch of a user-typed URL, so kept narrow — http(s) only, no redirects, 5 s timeout, capped bodies, only `system` + best-effort `containers`; it bypasses the cache).
- `containers.ts` — engine resolution, start/stop/restart, logs, and `listLocalContainers` (`ps -a` with published host ports, for setup's app suggestions; argv-only, empty on any failure).
- `stacks.ts` — compose stacks in `stacks.dir` (same dir Dockge uses). `up`/`down`/`restart` run as in-memory jobs that outlive the request; WebSocket subscribers get a snapshot replay then live output. One job per stack. Saves validate via `compose config` on a temp copy and keep `.bak` files. Containers map to stacks via the `com.docker.compose.project.working_dir` label.
- `alerts.ts` — the periodic sweep (sustain/repeat/recovery state machine) publishing to ntfy.
- `icons.ts` — `/api/icons/:slug`: fetches a dashboard-icons PNG once, caches it under `~/.cache/helm/icons` (or `$XDG_CACHE_HOME`), serves it immutable. Slugs are validated; misses are remembered for an hour.

**Frontend (`src/`)** — Ionic Vue 9, mobile first, target is the iOS home-screen web app (standalone Safari; no Capacitor). Components are plain JS `<script setup>`; TypeScript only for `main.ts`, `router/index.ts`, `vite.config.ts` and `App.vue`'s script. `main.ts` installs `IonicVue` with `mode: 'ios'` and imports Ionic's `core.css`, `normalize.css`, `structure.css`, `typography.css` (the documented order; typography is what enables Dynamic Font Scaling on iOS), its utility classes (`padding`, `flex-utils`, `text-alignment`, `display`) and `palettes/dark.system.css`, then `theme/main.css` and `theme/variables.css`. `App.vue` is `ion-app` + `ion-router-outlet`. `router/index.ts` (`@ionic/vue-router`) nests every route under `components/layout/TabsPage.vue` except the full-screen `/setup`: `/machines` (`/` redirects), `/machines/:id`, `/apps`, `/containers`, `/terminal`, and a catch-all not-found (Settings has no routes); a first-navigation guard migrates old `/?node=x` / `?tab=terminal` links and strips `?token=` from the address bar, and a second asks `/api/health` once per load and sends everything to `/setup` while `setup: true` (and `/setup` away once configured, unless a generated token is still waiting to be shown — `tokenPending()`). Page state lives in the query string.

- `components/layout/TabsPage.vue` — `ion-tabs`, one tab per `components/nav/navItems.js` entry (ionicons), tab bar on every screen size; also sets `document.title` and hosts the one Settings modal (lazy-loaded on first open, with the tabs' `ion-page` as the card's presenting element).
- `components/layout/HelmPage.vue` — every page's frame: native iOS nav bar (back button or Live status from `lib/connection.js`, title, `actions` slot, Settings), collapsing large title, `fixed` slot for direct `ion-content` children, shell notices (config failed, no machines).
- Pages in `src/pages/`, feature components in `src/components/<feature>/`, primitives in `src/components/ui/`: `BottomSheet.vue` (native `ion-modal` sheet with breakpoints on a phone, Ionic's centered card on wide screens, keyed on which; `footer` slot for primary actions), `SegmentedControl.vue` (`ion-segment`).
- Setup and Settings: `pages/SetupPage.vue` only sequences the steps (code → scope → this server → its apps → other servers → favorites → commands → token → review → done); progress, including the code, is in `sessionStorage` (`components/setup/wizardStore.js`). The forms are `components/setup/` (`ServerForm` with its Glances Test, `ServicesEditor`, `FavoritesPicker`, `CommandsEditor`, `StacksForm`, `GlancesHelp`, `CopyBlock`; `presets.js` command presets, `validate.js`), reused by `components/settings/`: `SettingsModal.vue` (iOS card modal; `can-dismiss` asks while anything is unsaved, `ion-nav` with `swipe-gesture` off while dirty), `SettingsRoot.vue` (the nav's root: rows that push `MachinesSettings` → `MachineSettings`, `AppsSettings`, `CommandsSettings`, `StacksSettings`, then the token), `SettingsView.vue` (every page's frame; Back swaps for a confirming button while dirty), and `editing.js` (save, `useUnsavedGuard`, `pushPage`/`leave`, `onConfigSaved`). `composables/useSettings.js` is the shared state: `open(section?)`, `close()`, the nav handle, the unsaved set. Setup calls carry the code (`X-Helm-Setup-Code`) to `/api/setup/*`; Settings uses `/api/admin/*`. A blank password field must be dropped before a Settings save, or the server reads it as "clear the saved password".
- Composables: `useMetrics.js` polls one node with self-scheduling (finish-then-wait, aborts on node switch, pauses when the browser tab is hidden or the page is inactive); `useFleet.js` runs one `useMetrics` per node for the pages that summarize all machines; `useStacks.js`; `usePageActive.js`, `useQuery.js`, `useConfirm.js` (iOS action sheet, resolves true only on the action), `useToast.js` (`ion-toast`, anchored above the tab bar).
- `lib/api.js` is the only fetch layer, same-origin in dev (Vite proxies `/api` with `ws: true`, and `/pty`) and prod; it takes `?token=` once and keeps it in `localStorage`. Settings' root sets the token for home-screen installs that can't be handed a `?token=` link, with a test-connection check (`/api/health`, then `/api/config`). `lib/attention.js` mirrors the alert rules for the home page's "Needs attention". `lib/history.js` holds per-node sparkline ring buffers (60 samples).
- The terminal page stays mounted because Ionic tabs keep it, so the shell survives tab switches; xterm is lazy-loaded on first visit, its font size follows the root font size, and the on-screen keyboard is handled via `visualViewport`. The `@` alias maps to `src/`.

Styling: no Tailwind or other CSS framework — Ionic's CSS, Ionic's utility classes (`ion-padding`, `ion-text-wrap`, `ion-justify-content-between`…), and plain custom properties on `:root` in `src/theme/main.css` (`--color-*`, `--font-*`, `--radius-*`), redefined for dark mode under `prefers-color-scheme`. `main.css` is unlayered and loads after Ionic's CSS; its reset covers what `normalize.css` leaves (text-block margins) and zeroes h1–h6, since every helm heading is styled by its own class. It targets plain HTML elements only, never `*` or `ion-*`, or it would strip Ionic components' own padding. All text is sized in rem. `src/theme/variables.css` maps Ionic's variables onto them (`--ion-background-color` = plane, `--ion-color-primary` = ink, danger = critical, …). Color means data or state only; no brand accent. Fonts are Quicksand (text) and Space Mono (numbers, identifiers, terminal), bundled via `@fontsource` — never loaded from Google. Controls are Ionic components; `main.css` holds only shared page classes (`.page`, `.page-title`, `.section-title`, `.note`, `.link`, `.num`, `.tabular`…). `index.html` holds the manifest link, apple-touch-icon and `apple-mobile-web-app-status-bar-style: black` (its comment explains why not translucent). Design rationale is in `docs/redesign/plan.md`.

**Deployment** — `install.sh` writes a systemd unit running `bun run server/index.ts` from the checkout as the installing user (not root), `HELM_CONFIG=/etc/helm/config.json`. It never writes the config: it creates `/etc/helm` owned by that user, mode 700 (so the server can write the config atomically and keep `setup-code` there), chmods an existing config to 600, and on a fresh install waits for `/etc/helm/setup-code` and prints the URL and code. Old installs re-run it once so `/etc/helm` becomes writable. `bin/tailnet-env.sh` runs as `ExecStartPre` to resolve the Tailscale IP on every start; the bind fails closed rather than widening. The terminal is a full shell, so never change defaults in a way that exposes the server beyond the tailnet/localhost.
